# Release Checklist

Use this checklist before publishing a demo/release. It verifies business correctness and deployment readiness; it is not a feature backlog.

## 1. Build Gates

Frontend:

```bash
cd frontend
npm ci
npm run quality:ui
npm run build
```

Backend:

```bash
cd backend
mvn verify
```

Do not deploy when either gate fails.

## 2. Database

- Confirm the target database and current Flyway version.
- Create a production database checkpoint/backup before new migrations.
- Never edit an applied migration.
- Verify the application reaches the expected migration version after deployment.

Current repository migration range: **V1-V14**.

## 3. Golden Business Flow

Use one customer and products with sufficient stock:

1. Accountant reviews Inventory and receives stock when a real inbound movement exists.
2. Sales creates a `DRAFT` order.
3. Confirm Draft creation does not change stock or receivables.
4. Sales confirms/completes the order using `SALES_ORDER_CONFIRM`.
5. Confirm stock decreases exactly once and an `OUT` transaction is recorded.
6. Confirm an unpaid amount creates one open receivable.
7. Accountant records a partial payment against that exact order.
8. Confirm only that order's receivable decreases.
9. Record the final payment.
10. Confirm the receivable closes and exactly one Draft invoice exists.
11. Issue/download the invoice and payment receipt.
12. Confirm dashboard/report/customer statement totals match the same canonical balance.
13. Confirm audit and notification entries are visible only to permitted roles.

## 4. Credit Limit

- Draft creation may warn about projected exposure.
- Fulfillment above a configured limit must fail before stock/debt mutation.
- Exposure exactly equal to the limit is allowed.
- `creditLimit = 0` remains unlimited/not configured.

## 5. Payments

- Outstanding list contains completed unpaid orders only.
- Partial payment remains traceable to PAY + SO + customer.
- Overpayment is rejected.
- Reusing the same request key does not create a duplicate payment.
- Receipt snapshot values do not change after later payments.
- Due-date filters follow `CURRENT`, `DUE_SOON`, `DUE_TODAY`, and `OVERDUE` semantics.

## 6. Products and Inventory

- New product code is generated by the backend.
- Product code is read-only when editing.
- Deactivated products remain in historical records.
- Deactivated products cannot be used for new sales or stock receiving.
- Low-stock alerts ignore inactive products where appropriate.
- Stock never becomes negative through fulfillment.

## 7. Tables and Filters

- Initial table state has no active sort arrow.
- Sort cycle is ascending -> descending -> neutral.
- Newest-first default data ordering remains deterministic.
- Multi-value status filters support checkbox selection.
- Search/filter/reset actions preserve pagination behavior correctly.
- Table headers/actions remain readable without unnecessary wrapping.

## 8. Roles

Verify at least the built-in demo roles:

- **Owner**: full business/admin flow.
- **Sales**: customer/product visibility, stock visibility, Draft order creation, and order completion within permission scope.
- **Accountant**: inventory receiving, receivables, payments, invoices, and reports within permission scope.

Also verify one custom role with dependent permissions.

## 9. Authentication and API Contracts

- Invalid credentials return `401`, never a generic `500`.
- The retired `warehouse` demo account cannot authenticate when demo mode is enabled.
- Paginated endpoints return only the stable page fields `content`, `totalElements`, `totalPages`, `size`, and `number`.

## 10. Language

- Switch VI -> EN and EN -> VI on each primary module.
- No mixed-language application copy.
- Invoice/payment PDFs use the requested language and render Unicode correctly.

## 11. Production Smoke Test

After deployment:

- frontend loads;
- public backend health returns 200;
- login works;
- dashboard, sales, customers, products, inventory, payments, invoices, reports, notifications, audit, and team routes open according to permissions;
- one non-destructive read flow works against production data;
- logs show no unexpected 500 errors;
- CORS origin is the production frontend URL.

Keep the previous deployable image/container and database checkpoint until the new release is verified.
